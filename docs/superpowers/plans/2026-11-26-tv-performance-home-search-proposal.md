## 1. 目标与结论

1. 解决首页到底后向上无法逐行回到顶部、焦点意外跳往导航的问题。
2. 无个人偏好时，首页以电影、剧集等点播内容为默认；直播仅为用户主动选择的独立入口。尊重已有个人信号，不承诺无内容源时凭空生成推荐。
3. 重设搜索筛选交互，明确焦点、已选条件与实际结果的关系；向下浏览结果时，导航向上隐藏、筛选压缩，始终可用遥控器返回。
4. 让跨源同作品更容易聚合、且聚合后的来源可真正选择；守住误合并、季、版本、播放身份和进度隔离的边界。
5. 针对可测的重组、图片、状态更新和玻璃绘制热点做局部优化；**不建议推倒 Compose TV 或 Media3 重写**。先测量，再决定是否需要进一步重构或调整材质。

### 1.1 范围与约束

- 唯一 TV 路由入口仍为 `TvRootApp`；保留手机 UI，API 26 可安装启动、Media3 生命周期及独立片源/剧集进度。
- 产品、焦点、Back、IME、播放、收藏和换源行为优先于性能数字。所有交互可 D-pad / OK / Back 操作，焦点不得丢失。
- 保留生产玻璃路径和视觉意图；不新增 WebView 电视路径、不更换 Haze/Liquid、不升级 Compose/Kotlin/compileSdk、不复制 GPL 代码或资源。
- Dialog 和播放器覆盖层维持 Basic；玻璃仅采样应用的静态 `BackdropLayer`，禁止采样视频 Surface、Dialog 或玻璃消费者。
- 不因模拟器结果预先限制玻璃面积、数量、效果或降档；实际变更须符合 G6 测量与 UX 门禁，保留完整效果复验路径。
- 不改正式金标阈值：mean ≤ 0.020、changed ≤ 0.08；视觉变更须重新采集受影响金标并人工评审。
- 不提交、推送或发布。本文件的未来实施步骤也不构成执行授权。

### 2.2 不应当作已证实的结论

- **首页跳导航的直接根因未复现。** 懒布局中的目标未附着、隐式二维焦点搜索、导航入口 requester 失联及跨行请求取消，都是可检验假设，不是已证实的框架故障。
- **“首页推荐默认直播”未在当前推荐链中发现。** 直播是独立模型和路由；LIVE 页面自动载入首个源不等于 HOME 自动推荐直播。须通过用户所见页面、配置与日志定位，不能顺手取消用户进入 LIVE 后的既有自动加载。
- **用户电视卡顿的主要来源未知。** 模拟器、旧 SHA、单个场景的结果不能证明真实电视的瓶颈；重组、GPU、解码、网络和焦点等待均需分层测量。
- `docs/evidence/2026-11-25-g6-glass-baseline.md` 的 9/9 组有效数据来自旧源码 `6768ab4…`、API34 Google TV AVD 和特定 `glassBenchmark` APK。该环境中 BLUR 的窗口 p95 高于 FULL，但它不是当前 SHA 的结果、显示 FPS、电视预算或物理设备证明。
- 搜索标题相同不等于同一作品；缺失年份、类型、季与权威 ID 的真实比例尚未量化。任何合并率或误合并率都必须来自脱敏样本和对照集。

## 3. 方案选择与总体结构

### 3.1 比较

- **整体重写 UI / 换技术栈：不推荐。** 会重开焦点、API26、播放、玻璃及验收风险，且尚无证据证明现有架构本身是卡顿根因。
- **仅打补丁、隐藏部分控件：不推荐。** 无法解决搜索头部所有权、聚合后的来源不可达和离屏焦点协调，容易产生新焦点陷阱。
- **推荐：局部结构调整 + 分层测量。** 保留根路由、焦点登记、懒列表和生产玻璃；只重构首页纵向焦点协调、搜索 chrome/筛选与作品展示聚合边界，再按测量处理性能热点。各单元可独立测试及回滚。

## 4. 首页：纵向焦点与默认推荐

### 4.1 焦点契约

1. 首页内依次形成 hero、继续观看、电影、剧集、发现等**实际存在的可交互区域**；空行和仅状态文字跳过。区域顺序随当前数据变化实时更新。
2. 货架内 Up 到前一个可交互区域、Down 到下一个区域；目标尚未组合时先定位父 `LazyColumn`，再准备目标 `LazyRow` 并请求对应稳定 key。**从最后一行向上不得越过中间存在的行直接跳导航。**
3. 到达最上方可交互内容后再按 Up 才进入导航；hero 为空、某行被删除、无结果、加载中、错误态、首行无卡片时均有确定的可达后备目标，不得出现不可见焦点。
4. 焦点保持同一列或该行上次焦点键；目标消失时按旧位置限制到有效范围，仍不存在则落到该行第一个可用目标。禁止因一次失败直接跳导航。
5. 导航 Down 在内容节点离屏时应先准备最近有效的首页书签/入口，再恢复焦点；用户后续输入、页面切换、数据刷新、旧任务超时均取消旧请求，不得抢回焦点。
6. 保留横向快速移动与 `FocusRestorationGuard` 的既有逻辑；不要把所有 Up/Down 一概吞掉，行内控件、错误动作、Back、IME 和系统事件仍由原有 owner 处理。

**可能涉及：** `HomeScreen.kt`、`ContentRail.kt`、`TvFocusRegistry.kt` / `FocusRestoration.kt`、`FloatingNavigation.kt`；必要时新增纯逻辑 `HomeFocusTraversal.kt`。先证明问题，再选最小改动；不要无证据地大改全局 `BringIntoViewSpec` 或所有页面。
当前 `ContentRail` 的 region key 含展示标题；需评估既有书签兼容后再引入稳定语义键，不能仅改文案造成恢复丢失。极大字号时，现有 `ContentRailVisibilityTest.kt:426-438` 允许跳到导航；本方案要求目标仍存在时先准备并到达 hero，因此需明确修订该测试并保留“滚动收敛、不抢回焦点”断言，不得悄悄保留旧例外。

### 4.2 冷启动与空态

1. 检测已有有效个人信号，继续使用现有推荐策略与隐私边界；没有信号时按**电影优先、剧集其次**，同类内使用合法目录提供的稳定顺序。不得把 `mediaTypeKnown=false` 的条目默认为电影。
2. Hero 候选优先已可用电影，其次剧集；再考虑现有点播搜索发现结果并标识其来源/类型不确定；无候选则清晰展示空态。无需改变“继续观看”货架原有位置和用户已有偏好。
3. 可用推荐源按现有架构分别检查：合法元数据目录、允许展示的本地数据、用户已配置 VOD 搜索发现；是否具备匿名公共榜单须以实际实现及网络/许可为准。不可承诺离线、未连接服务或无数据时仍能看到海报。
4. 空态提供可达的“电影/剧集”或“搜索/配置服务”路径，依据连接状态给出正确说明；直播保留独立导航，**不作为默认兜底**。
5. 先为“用户看到直播推荐”的实际路径补可复现夹具（包括仅有直播源、无 VOD 源、旧配置和未知类型）。仅在定位到真实错误后修相应入口；不修改 `navigate(Page.LIVE)` 的加载语义作为猜测性修复。
6. 区分“应用启动入口”和“HOME 内容”：当前未连接服务时启动到 SETTINGS，不得把仅有直播源等同于已进入 HOME。检查 `LibreTvRepository.kt:159-170` 的目录类型解析是否将缺失/非法 `type` 当作电影，以及 `movieInput` 对未知类型的处理；补解析和筛选边界测试，不只修改 hero 的呈现规则。

**可能涉及：** `CinemaViewModel.kt`、`HomeScreen.kt`、`data/recommendation/LocalRecommendationPipeline.kt`、`HomeDiscoveryStore.kt`；必要时抽出小型纯策略，而不是引入与现有排序重复的第二套推荐引擎。

## 5. 搜索：筛选与浏览界面

### 5.1 建议界面

```text

                     搜索  [片名、别名或演员          ] [搜索]
                     [类型：全部] [年份：全部] [评分：全部] [更多筛选]
                     最近搜索 / 结果状态
                     [海报] [海报] [海报] [海报] …

浏览 / 向下：        导航向上隐藏（不可聚焦、无屏幕占位）
                     [搜索词：……] [电影 · 2024 · 豆瓣≥8] [筛选]
                     [海报] [海报] [海报] [海报] …
                     [海报] [海报] [海报] [海报] …

筛选展开：           类型       全部 / 电影 / 剧集
                     年份       全部 / 可用年份……
                     榜单与评分  全部 / TMDB≥8 / 豆瓣≥8 / 豆瓣 TOP250
```

以上为结构草图，不是最终视觉金标。沿用现有 TV token 与玻璃体系；小视口、长文案和放大字体不允许遮住结果或截断有效状态。Compact 必须通过实际测量比展开态给网格更多可见区域；具体 dp 不先写为“已达到”。

### 5.2 筛选语义

- 按**类型、年份、榜单/评分**分组；每一组显示当前值，“焦点框”“已选状态”和“禁用状态”在视觉及 semantics 上各自可辨，不仅依赖颜色。
- 推荐每组单选，选择当前选项可返回该组“全部”；“清空筛选”明确清空的维度，不能误清查询文本。不可用的数据源/标签说明原因，不能伪装为已选。
- 评分来源采用明确文案，例如“豆瓣来源 · 评分≥8”；保持现有逐来源筛选语义，不将不同平台分数当成可直接比较的统一分数。豆瓣标签与评分是否组合，以筛选状态的真实字段表达，切换后不显示虚假的 ≥8 标记。
- 筛选摘要列出所有有效维度；放不下时可折叠为可聚焦的“筛选 N 项”，进入后可查看完整条件。
- 确认查询或修改筛选后，新结果集从顶部展示并给出明确焦点；从详情/播放返回同一结果集则恢复原有焦点与滚动。两种路径必须区分，避免异步重算把用户拉回顶部。

### 5.3 顶栏隐藏状态机和遥控器

**推荐状态：**

- `Expanded`：进入页面、输入/IME、焦点进入搜索或筛选区，或没有可浏览结果而处于空、加载或错误状态时，显示完整可操作头部和导航。
- `Browsing`：存在可浏览结果且用户从结果首行继续向下移动时，导航向上移出并禁用其焦点；筛选区缩为一行摘要，结果区取得空间。具体触发使用结果行/焦点和滚动状态，入口/退出有迟滞，避免动画抖动。
- `FilterOpen`：从摘要的“筛选”进入，展开分组选择；退出回到原结果焦点或调用入口。输入和 IME 优先于浏览态。

**明确按键：**

1. 结果网格内 Up/Down 正常逐行移动；任何非首行 Up 都不得跳到筛选/导航。
2. 结果首行 Up → 焦点进入精简筛选摘要；再次 Up → 展开并恢复导航，焦点落到当前导航入口。摘要的 OK 打开筛选，选择完成回到原结果项。
3. 导航恢复之前不得把不可见导航留在焦点树；恢复后焦点转移与动画顺序应原子化，防止落入空焦点。还原原始 `SaveableStateHolder` / `FocusCoordinator` 的路由与 key 契约。
4. IME 可见时第一下 Back 收键盘并留在 SEARCH；原有 SEARCH Back → HOME 规则不变。筛选若采用浮层，Back 先关闭该浮层，再沿用原路由规则；Back 不单独被浏览态消耗。
5. 从 DETAIL/PLAYER 返回深层结果时保留结果 key 和位置：先恢复并准备目标，依据已保存浏览上下文恢复 chrome；不因“首帧强制展开”闪跳或因旧协程抢焦点。快速反向键、数据到达及路由切换必须取消过时动作。
6. 减少动态布局时的焦点位移；Reduced Motion 使用无空间动画或简化过渡，但状态、可达性、焦点轮廓和文字对比不变。

7. 流式搜索时，有结果且焦点仍在网格内，即使 `busy` 变化也保持浏览态；结果变空、错误使结果不可用、用户进入输入/筛选或切换路由时安全展开，先安置焦点再移除节点。不能让每个来源到达时反复展开收起。

**所有权和空间：** `TvRootApp` 仍是导航唯一 owner；搜索页只发布有生命周期的显示意图，离开 SEARCH 自动清理。导航的可用性和 `TvNavigationFocusOwner` 必须与隐藏状态一致，并正确清理 `navigationHasFocus`、避免恢复阶段抢焦点；保持现有 `SaveableStateHolder` / `FocusCoordinator` 路由及 key 契约。当前导航是 overlay，隐藏它本身**不会**释放 `SearchScreen` 的 `layout.contentTop` 留白：需增加仅搜索页使用的浏览态 inset（或等价局部契约），不得直接全局改 `TvTokens.contentTop` 影响其他页面；若发现必须改共享 token，先评估其他页面及全部受影响金标。不得由页面创建第二套导航或第二个根路由。实现可考虑带全宽头部 item 的懒网格或条件头部，但需以焦点原型测试证明可达性，不预设 Compose 某 API 自动处理离屏节点。

搜索历史目前由现有本地存储保存；本方案默认不新增查询、筛选或浏览上下文的持久化。若将来新增持久化，须先说明保存范围、期限、隐私及可访问的清除路径，并测试清除和重启恢复。

## 6. 搜索：跨源作品聚合

### 6.1 设计边界

- 聚合只改变**展示组**，保留每个原始来源的 ID、源身份、剧集、播放地址处理和本源续播记录；禁止以展示组 ID 覆盖播放或进度 ID。组内每个成员须保留其归属、许可与到期状态；只显示有权展示、仍有效的内容及必要署名，不得因切换代表而漏署名或延长许可。
- 强匹配优先，弱匹配不自动合并。当前计数是组内去重来源数，**不是测活结果**；目标默认标注“N 个来源”，不承诺均可播放。若未来显示“可用来源数”，须有独立、限流、过期明确的测活证据；来源内多个版本单独标识，不能错误计数。
- 保留 `data/` 中解析 provider JSON 与身份判定；UI 只接收有界展示 DTO 和安全的来源名称等，不接收凭据、Cookie、任意 URL 或完整 ViewModel 以外的新泄露面。

### 6.2 分层规则

1. **强身份**：同一可信命名空间、同一外部 ID，且无已知类型、季、其他权威 ID 的冲突时可合并；权威 ID 本身的粒度必须区分剧集作品/季/电影。**季约束优先于作品级 ID**：同一系列级 ID 并不能证明是同一季；双方都缺季或一方缺季时，仅有系列级 ID 仍不自动跨源合并，只有可信、粒度明确的同一季级 ID 才能例外。**同 ID 跨译名合组是相对当前实现的放宽**，须先验证来源可信性和跨语言、电影/剧集同号负例。年份冲突不静默覆盖：电影默认拒绝；剧集需要明确首播年与季年份的语义后才能放宽。外部 ID 必须来自可追溯的可信映射，不能仅靠标题猜出。
2. **完整复合身份**：规范标题、已知类型、年份及适用的已知季信息一致，且无权威 ID 冲突时合并；不同季、翻拍、电影/剧集冲突不合并。默认情况下剧集双方都缺季也不跨源自动合并，除非有可确认的同一季权威身份；当前 `workKey` 会把两个 `unknown` 季合为一组，这是需要回归覆盖的现状风险，不是既有保证。版本后缀、译名和简繁转换不得仅凭字符串相似度自动合并。
3. **证据不足**：年份/类型/季缺失或别名相似而无可信 ID 时，默认分组分开；可展示“可能相关”，但不得作为事实或自动合并。确有需求时复用现有本地人工关联能力，先确认关联范围、撤销及 UI 可达性，再作为独立后续项。
4. **补全先于放宽**：先核对已有目录/BFF/豆瓣合法元数据是否能可靠提供年份与权威 ID；仅对受限数量、高相关条目按授权和既有网络策略补全，支持取消、缓存、超时、空结果，不记录用户查询或源 URL 到诊断日志。现有 `enrichMetadata` 使用阻塞连接和超时，不保证协程取消中断网络；可取消性是额外工作，不能声称已有。补全失败继续显示原结果。
5. **一致性而非强行统一所有谓词**：比较 `workKey` 与 `sameWork` 对未知季的差异、`MediaIdentity.isSameWork`、详情换源候选及 `MediaDomainMapper` 的不同用途；对照 `explicitIds` 支持任意命名空间而 `workId` 限定若干命名空间的差异。提取共享证据和冲突规则，但搜索展示、目录解析、用户关联、播放恢复可保留各自更严格的策略。迁移必须覆盖旧数据与现有库语义。
6. 豆瓣来源必须遵守既有显式使用、公开数据和许可门禁；本方案将“非豆瓣筛选的中性搜索不展示豆瓣评分或 TOP 排名、不以豆瓣成员替换中性代表”设为目标展示约束。当前已有本地保存的豆瓣条目经 `repo.localItems()` 进入搜索代表并显示评分/排名的静态可达路径，是否实际显示还受数据与许可状态影响。阶段 D 必须用合成夹具验证并在此范围内处理，不得仅记录后放过；来源署名及有效许可按实际展示内容逐成员保留。

### 6.3 可选来源与异步稳定

- `SearchHit` 及其成员经有界 DTO 传给电视和手机展示层；进入详情/来源选择时保留每个来源可达，避免只展示组代表。优先复用详情已有换源交互，并保证遥控器与 Back 可达；无须强加长按作为唯一入口。
- 选择来源时复用现有受限解析器校验目标身份、解析并检查可播放地址，不预先对 N 个成员逐一发起播放探测。现有上限为最多 3 个查询、6 次详情和 75 秒总超时；后续可以缩紧但不能无评审放大。失败、超时或取消时保留原片源并提示重试；同源多个版本允许区分，不以 `distinctBy(sourceUrl)` 意外吞掉不同版本。继续使用该来源自己的剧集身份和进度；不能声称跨源续播一定可用。
- 流式增量与 `done` 重排使用稳定**展示组键**，不依赖先返回的第一张海报或来源顺序。新证据令两个组安全合并时，显式迁移旧组 key → 新组 key、焦点书签和滚动锚点；若当前焦点项消失，选择其包含成员的组并安全恢复。新搜索 generation 到来后取消旧结果，不能混入旧查询。
- 保留部分成功与错误提示；来源中断时不伪称搜索完成，允许重试。不因为“单调增加”要求忽视上游撤回、过滤或冲突拆分：这些情况要明确的更新规则与回退焦点。
- 离线合成集覆盖同名翻拍、跨年上映、未知年/类型、不同季、**双方缺季、一方缺季、同系列 ID 但季未知、同一可信季级 ID**、电影/剧集、别名、同 ID 冲突、相同来源不同版本、异步倒序和部分失败，分别测**漏合并与误合并**。

**可能涉及：** `data/SearchAggregator.kt`、`SearchIndex.kt`、`MediaIdentity.kt`、`MediaDomainMapper.kt`、`LibreTvRepository.kt`、豆瓣公共解析、`CinemaViewModel.kt`、`SearchScreen.kt`、详情与手机对应页面；元数据扩展如确有必要再涉及 `backend/tv-bff/`，不先扩大协议。

## 7. 性能：证据驱动的局部优化

### 7.1 建立可比较基线

未来执行时先对**精确候选**测冷启动、首页上下/左右跨行、海报切换、搜索输入与筛选、流式多源结果、详情返回和播放器返回；记录输入→状态→绘制帧、p50/p95/p99、deadline jank、内存与必要的主线程/渲染线程/GPU 线索。帧 deadline 取实际 deadline 或刷新率回退，不把 16.67 ms 固定当所有设备阈值。

- 使用真实压缩图片的**自制/合成测试夹具**，不打入生产包；记录图片大小、冷暖缓存、结果数量及实际 GPU renderer。
- 沿用 `scripts/native-tv-perf/`、`scripts/glass-performance/` 与 `docs/TEST_PLAN.md`；校验真实绘制档位、输入配对和采样有效性。`glassQuality` 与 `tierDirect` 必须匹配，不能把空窗口当通过。
- 在相同设备、场景、renderer、分辨率、档位、图片和输入脚本下交错前后对照；记录源码 SHA、APK SHA-256、构建类型、样本、异常和 95% 区间。先评估 run 间噪声，再判断改善/回归。
- 按需用测试构建加入受控计数，统计重组、解码请求、层录制或搜索重算；采集本身也要测开销。不要保存真实标题、播放地址、凭据和用户个人内容。
- 模拟器 E-gate 只说明协议和同环境相对变化；真实 TV 的 T-gate 为 owner 可选运行，不做则明确未运行，不据此声称产品 FPS 或真机体验。

### 7.2 按证据排序的候选，不预设收益

| 优先级 | 候选 | 验证和护栏 |
|---|---|---|
| P0 | 确认首页/搜索焦点等待和滚动状态；补性能/功能复现夹具 | 输入回执与绘制帧配对；先确保操作正确，再看速度 |
| P1 | 缩小 root 状态读取和无实际消费者的回调；将频繁变化的读取下沉到需要它的组件 | 用重组计数验证；不能丢失生产场景 decoded 通知、错误提示或导航状态 |
| P1 | 测 `GlassAction` 动画参数和 backdrop 层失效；参考已有卡片在绘制/图层阶段读取状态的模式 | 独立 A/B，同材质同视觉；不修改光学 shader 和失败回退，不假定每帧一定重新建满所有层 |
| P1 | 背景预取尺寸与显示请求协同，评估一次请求供校验/显示 | 以实际 Coil 请求、缓存命中、解码次数、PSS 验证；不能断言尺寸不一致就一定无法复用；保留图片比例校验、失败回退和生命周期取消 |
| P1 | 审查库快照、定时排序、搜索逐源重算及大列表比较 | 基于事件/版本拆分无关更新、取消过期任务、批量化；播放进度、收藏、过期许可、搜索实时性不可退化 |
| P2 | 若瓶颈仍在离屏录制或材质，评估缓存和无效化边界 | 每次只改一个变量，验证静态/动画/背景变化/窗口重建不显示旧图；Full/Blur/Basic 和 API 回退分别测 |
| P3 | 仅经目标场景实测确有必要时，评审 G6 范围的面积/并发/材质策略 | 先保证焦点、对比、清晰度和完整效果复验；相关设备验证，不能以模拟器单次结果授权降级 |

不盲目删除安全底色、不将所有图统一解码到大尺寸、不为速度关闭焦点动效或永久冻结背景；这些都可能增加内存或破坏可读性。对于未观察到收益或不再成立的热点直接放弃，不以“重构”本身为目标。

### 关键失败案例

1. 深滚后搜索结果增量合组、代表变动或源取消，焦点必须保留在包含原结果的组或可见安全后备。
2. 结果首行以外按 Up 不得跳过结果；导航隐藏时任何不可见节点不得持有或夺取焦点。
3. 同名不同季、翻拍或冲突 ID 不得误合并；缺失字段不得把未知类型当电影。
4. 快速切页、连续方向键、IME、Dialog、播放返回时，过时协程不得抢焦点或覆盖新数据。
5. 单一来源失败、目录未配置、无授权数据、无海报或离线，页面保留可解释空态与可操作入口，不能虚构内容或暴露凭据。
6. 状态更新优化不能使播放进度、收藏、筛选、来源数或许可证过期显示陈旧；图片缓存优化不能造成错误海报或超预算内存。
